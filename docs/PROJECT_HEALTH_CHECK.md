# Smart Home Project Health Check

_Last updated: 2026-05-15 16:54 ADT_

This health check reflects the repository state after the backend modularization, API-key hardening, root README cleanup, and the current critical remediation PRs:

- PR #10: `fix/docker-build-context-secrets` — adds `backend/.dockerignore` and documents Docker build-context boundaries.
- PR #11: `fix/structured-startup-logging` — adds structured JSON stdout logging and logs startup mock-device seed failures.

Status legend: ✅ Good / ⚠️ Needs Attention / ❌ Critical.

## 1. Project Structure — ✅ Good

### What's good
- Backend concerns are separated into `routers/`, `services/`, `schemas/`, `core/`, and `ha_client.py`.
- `main.py` is intentionally thin: FastAPI app creation, router registration, and startup seeding only.
- Root `README.md`, `docs/PROJECT_DOC.md`, `docs/HA_BACKEND_API.md`, and `docs/BACKEND_CODE_GUIDE.md` describe setup and architecture.

### Missing or risky
- The docs are broad but scattered. New contributors need a single health/status document that maps feedback to remediation work.

### Exact next step
- Keep this file (`docs/PROJECT_HEALTH_CHECK.md`) as the current status source for health-check feedback and remediation tracking.

## 2. Security — ⚠️ Needs Attention

### What's good
- Control/data routes are protected with `X-API-Key` via `SMART_HOME_API_KEY`.
- Diagnostic routes intentionally remain open: `GET /` and `GET /ha/health`.
- Root `.dockerignore` excludes `.env*`, Home Assistant runtime config, virtualenvs, logs, caches, and VCS noise from root Docker builds.
- PR #10 adds `backend/.dockerignore` for backend-subdirectory builds.

### Missing or risky
- Until PR #10 is merged, `context: ./backend` builds do not have a backend-local ignore file.
- SSH hardening cannot be verified from repository files alone; verify it on the Orin host.
- No role-based or user-level API authorization exists; the current control-plane protection is a shared API key.

### Exact next step
Merge PR #10, then verify secrets are excluded from every Docker context:

```bash
git checkout main && git pull
find . -maxdepth 3 -name '.dockerignore' -print
python3 .github/scripts/secret_scan.py
```

On the Orin, verify SSH hardening:

```bash
sudo sshd -T | grep -E 'passwordauthentication|pubkeyauthentication|permitrootlogin'
```

Expected direction:

```text
passwordauthentication no
pubkeyauthentication yes
permitrootlogin no
```

## 3. Docker & ARM64 Compatibility — ⚠️ Needs Attention

### What's good
- Home Assistant has `restart: unless-stopped`.
- Root `.dockerignore` exists.
- The health-check feedback identified the need for explicit ARM64 build/deploy validation before relying on the Orin Nano deployment.

### Missing or risky
- `docker-compose.yml` still uses `ghcr.io/home-assistant/home-assistant:stable`; this is not pinned to an immutable version or digest.
- `docker-compose.yml` does not currently declare `platform: linux/arm64` on `main`.
- The backend does not yet have a merged Dockerfile/deploy workflow on `main`.
- If backend builds use `context: ./backend`, PR #10 must be merged first so secrets are not sent to Docker.

### Exact next step
Open/merge a separate ARM64 compatibility PR after PR #10:

```yaml
services:
  homeassistant:
    image: ghcr.io/home-assistant/home-assistant:<pinned-version-or-digest>
    platform: linux/arm64
    restart: unless-stopped

  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    platform: linux/arm64
    restart: unless-stopped
```

Add CI validation:

```bash
docker buildx build --platform linux/arm64 -f backend/Dockerfile backend --load
docker compose config >/dev/null
```

## 4. FastAPI Code Quality — ✅ Good

### What's good
- Endpoints use Pydantic request/response schemas in `backend/schemas/ha.py`.
- HA failures are mapped through `HomeAssistantError` and `core/errors.py`.
- `GET /ha/health` checks HA API connectivity.
- OpenAPI is generated by FastAPI and backed by explicit router functions and schemas.

### Missing or risky
- Some endpoint examples in docs must include `X-API-Key` for protected routes to avoid copy/paste failures.
- The docs should keep production path guidance clear: use `POST /commands` for automation; use `/services`, `/devices`, and `/mock` mostly for diagnostics/manual work.

### Exact next step
When editing endpoint docs, include the header on protected calls:

```bash
curl -X POST http://127.0.0.1:8000/commands \
  -H "Content-Type: application/json" \
  -H "X-API-Key: $SMART_HOME_API_KEY" \
  -d '{"schema_version":"ha-bridge.v1","message_type":"ha.command.request","request_id":"req_001","intent":{"domain":"light","service":"turn_off","entity_id":"light.mock_bedroom_lamp"}}'
```

## 5. Home Assistant Integration — ⚠️ Needs Attention

### What's good
- `ha_client.py` centralizes HA REST calls and prefers `HA_URL`, `HA_TOKEN`, and `HA_TIMEOUT_SEC`.
- Command execution performs before/after reads and verification when requested.
- Mock device safety requires `attributes.mock_device: true` for mock convenience controls.

### Missing or risky
- The project context says FastAPI connects to HA via SSH, but current backend code uses the HA REST API. If SSH is still part of deployment/ops, it is not represented as a backend integration layer.
- Entity IDs are passed in request payloads and mock defaults live in code; there is no environment/config registry for production entity aliases yet.

### Exact next step
Clarify the integration boundary in docs/config:

```env
HA_URL=http://homeassistant:8123
HA_TOKEN=YOUR_HOME_ASSISTANT_LONG_LIVED_ACCESS_TOKEN
HA_TIMEOUT_SEC=10
```

If SSH remains required, document it as deployment/ops access, not as the runtime HA control path, unless code is added for SSH-based HA commands.

### Missing or risky
- Until PR #11 is merged, startup seed failures can be silent.
- No alerting is configured for FastAPI or HA downtime.
- Log persistence/rotation policy is not documented for the Orin deployment.

### Exact next step
Merge PR #11, then verify logs include structured JSON after a startup failure:

